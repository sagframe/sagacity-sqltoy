## 一、严重缺陷（数据损坏 / 越权 / 服务不可用，最高优先级）

### S1. 批量更新尾随 null 行导致整批数据静默丢失 【已修复 2026-08-14】
- **位置**：`utils/SqlUtil.java:1414-1467`（batchUpdateByJdbc）、`utils/SqlUtilsExt.java:104-139`（batchUpdateForPOJO，同样模式）
- **修复方式**：循环内仅在达到批次量时 executeBatch，循环结束后统一补齐未执行的尾部批次（对不含 null 行的集合行为完全等价）；回归测试 `src/test/java/org/sagacity/sqltoy/utils/SqlUtilBatchUpdateNullTailTest.java`（5 用例，修复前 3 例失败复现数据丢失，修复后全部通过）
- **问题**：`executeBatch` 的触发条件 `index == totalRows` 位于 `if (rowData != null)` 块**内部**。当集合末尾一行或多行为 null 时，之前已 `addBatch` 的语句永远不会被 `executeBatch`，`finally` 中 `pst.close()` 直接丢弃，**数据不落库且无任何报错/日志**，返回的影响行数也偏小。
```java
if (rowData != null) {
    ...
    pst.addBatch();
    if ((meter % batchSize) == 0 || index == totalRows) {  // index==totalRows 只在非null行内判断
        int[] updateRows = pst.executeBatch();
```
- **影响**：saveAll/updateAll 传入含 null 元素的集合（业务层常见）时尾部整批数据丢失。

### S2. 分表策略负 hash 取模返回 null，静默写错表/错库 【已修复 2026-08-14】
- **位置**：`plugins/sharding/impl/HashShardingStrategy.java:52-56（分表）、75-78（分库）`
- **修复方式**：两处 `hashCode % mode` 改为 `Math.floorMod(hashCode, mode)`，负 hash 归一到 `[0, mode)`；回归测试 `src/test/java/org/sagacity/sqltoy/plugins/sharding/impl/HashShardingStrategyTest.java`（3 用例，修复前负 hash 用例返回 null 复现路由失败，修复后全部通过）
- **问题**：`hashCode % tableMode` 可为负（String/Long 的 hashCode 均可能为负），`tableMap.get("-3")` 返回 null；`ShardingUtils.getSharding:107` 对 null 判空后**静默回落基准表**，数据写入未分片的原表；分库同理落到默认库。属数据路由错误而非报错。
```java
String modeKey = Integer.toString(hashCode % tableMode);
return tableMap.get(modeKey);
```
- **修复**：改用 `Math.floorMod(hashCode, tableMode)`。

### S3. 租户拦截器租户值未转义直接拼入 SQL 字面量 【已修复 2026-08-15，含审计勘误】
- **位置**：`plugins/interceptors/TenantFilterInterceptor.java`
- **审计勘误**：原判定"多租户分支走了 combineQueryInStr 转义、单租户分支遗漏"**不准确**——经查 `combineQueryInStr` 也只是引号包裹无转义，**两个分支同样存在**该问题。
- **威胁面定级（经质询核实）**：租户值来自应用实现的 `IUnifyFieldsHandler` 回调，典型部署下来自会话/JWT/内部系统编码，实际可利用性低（需租户开通链路放行含引号 ID）；但框架不能替应用担保上游值干净（外部合作方编码、迁移数据、第三方 IdP claim 等场景真实存在），属**防御纵深缺失**类安全缺陷，非"必然可利用"。
- **修复方式**：新增 `escapeQuote`（`'`→`''` 标准SQL转义，主流库通用），单租户 `=` 分支与多租户 `in` 分支**统一**转义（in 分支改为显式逐值拼接，不再经无转义的 combineQueryInStr）。
- **回归测试**：`TenantFilterInterceptorTest`（3 用例：`T001' or '1'='1` 被禁锢在字面量内、in 分支含引号值逐个转义、正常租户值不变；反向验证用父提交版本实测旧代码 2 用例失败——未转义引号直接进入 SQL）。

### S6. 翻译缓存增量更新线程直接并发修改 HashMap 【已修复 2026-08-15】【定级勘误：严重→低，2026-08-15 经用户质询复核】
- **位置**：`translate/CacheUpdateWatcher.java`（写点 261/284/288）+ `TranslateManager.java:141`
- **修复方式**：标准缓存路径（`translateCacheManager`，不绑定具体实现）的增量更新改为**复制-整体原子写回**——新增 `applyStandCacheIncrement`（复制 getCache 返回的 map → 副本上应用全部更新 → 经 `translateCacheManager.put` 原子写回），业务翻译线程持有的旧 map 引用从此**冻结不再被修改**（冻结发布语义），新读者原子切换到新 map；分组缓存按 cacheType 分组后每组替换一次。**契约依据**（已核证官方两个实现）：`put` 语义为"存储给定 map 作为缓存内容"——ehcache（`cache.put(key, value)` 整体替换）与 caffeine（`cache.put(key, value)` 同）一致且首装流程依赖此语义；对 put 为合并语义的自定义实现，方法退化为单次批量合并（竞争窗口从 N 次收窄为 1 次），已在 javadoc 如实标注。动态缓存路径（FIFOMap）维持 containsKey 守卫的**已存在键值替换**（仅引用赋值、无结构变更，可接受残留）。watcher 线程改 daemon 并命名 `sqltoy-cache-update-watcher`，两处 InterruptedException 补恢复中断标志。
- **定级勘误（用户质询后复核）**：原判"可能读到损坏桶/扩容期间死循环"**对实际并发形状评重了**——该故障需两个并发结构性写者，而 CacheUpdateWatcher 是单线程（15秒+间隔、有变更才写）；JDK8+ HashMap 在单写多读下的退化仅为瞬时脏读/漏读（自愈、不可观测）；读者 99.99% 是纯 get，唯一遍历点（TranslateManager:207 长度校验）的 CME 窗口仅数条指令宽。**实际定级：低（理论数据竞争，触发窗口极窄）**。唯一真实的结构性风险：TranslateEhcacheManager.cacheManager 为 static，同 JVM 双上下文配同名增量缓存时才会出现双写者（罕见部署形态）。修复保留（正确且代价可忽略），但严重度排序以本勘误为准。
- **回归测试**：`CacheUpdateWatcherIncrementTest`（3 用例：增量替换后旧 map 冻结【既有键值不变、新键不出现】、新 map 含全部更新与既有数据、分组按类型替换、daemon+命名）。反向验证说明：本修复含方法重构（applyEhCacheIncrement），旧代码下测试无法编译，旧缺陷形态（直接 put 共享 map）由"旧 map 冻结"断言结构性覆盖。
